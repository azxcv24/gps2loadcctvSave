# ADR-0002: 시각 기준과 CCTV 시계 오차 모델

- 상태: 제안
- 날짜: 2026-10-26
- 결정자: (저장소 소유자 승인 필요)

## 문맥

README 초안의 예시는 "권장 확인 범위"가 표준시 기준인지 CCTV 화면 시각 기준인지 밝히지 않았고, 수치(14:31:20 ~ 14:33:00)도 계산 과정과 맞지 않았다. 시각 오차의 부호 규약, 오차 근거가 오래될수록 불확실성이 커지는 점, 근거가 전혀 없을 때의 처리도 정해져 있지 않았다.

## 결정

1. **저장은 모두 UTC**, 표시는 설정한 시간대(기본 Asia/Seoul). 시간대가 없는 입력은 `--assume-tz`를 주지 않으면 거부한다.
2. **오차 부호**: `offset = CCTV 화면 표시 시각 − 표준 시각`. 음수면 CCTV 시계가 느리다.
3. **세 가지 범위를 구분해 모두 기록한다.**
   - 확인 범위(표준시): GPS 경로로 계산한 실제 시각 범위
   - CCTV 시계 기준 범위: 표준시 범위 + offset ± 불확실성
   - **보존 요청 권장 범위(CCTV 화면 표시 시각)**: 위 두 범위를 모두 덮고 `request_rounding_seconds`(기본 10초) 단위로 바깥쪽 반올림. 오차 추정이 틀려 실제로는 CCTV 시계가 정확한 경우까지 포함하기 위함.
4. **오차 근거**: `manual_observation`(사용자가 같은 순간의 표준 시각과 CCTV 화면 시각을 비교) 또는 `provider_declared`(제공처 고지). 통과 시각에 가장 가까운 근거를 쓰고, 불확실성은 `기본 불확실성 + 하루당 드리프트 × 경과 일수`로 늘린다.
5. **근거가 없으면** offset 0, 불확실성 ±180초(설정)로 보수적으로 잡고 신뢰도를 "낮음"으로 표시해 사용자 검토로 넘긴다.
6. 보존 요청 범위가 15분(설정)을 넘으면 자동 판단하지 않고 사용자 검토 또는 제공처 문의로 전환한다.

README 예시는 `tests/test_candidate_math.py::TestReadmeExample`이 그대로 재현한다.

## 결과와 위험

- 범위가 보수적으로 넓어지는 대신, 시각 오차 추정 실수로 자료를 놓칠 위험이 줄어든다.
- 기본 드리프트(하루 2초)와 무근거 불확실성(±180초)은 가정값이다. 실제 제공처의 시각 동기화 방식이 확인되면 조정해야 한다.

## 재검토 조건

- 첫 공식 제공처의 시각 동기화 방식(NTP 등)과 영상 타임스탬프 기준이 확인될 때
- 제공처가 보존 요청을 표준시로 받는지, 화면 표시 시각으로 받는지 확인될 때
