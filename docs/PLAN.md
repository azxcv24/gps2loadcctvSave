# 프로젝트 실행 계획

## 1. 문서 상태

- 상태: 초안
- 기준일: 2026-10-26
- 프로젝트 성격: 사고 증거 보존 및 공식 CCTV 자료 연계 보조 도구
- 우선순위: 안전성, 합법성, 최소 수집, 삭제 가능성, 시간 정합성
- 구현 상태: v0.2 — GPS 기반 실시간 자동 녹화(14절) + v0.1 수동 사건 처리. 문서 검토 결과는 13절 참고

## 2. 제품 정의

블랙박스가 고장 나거나 사고 영상이 저장되지 않은 경우, 사고가 발생한 시간과 위치 주변의 공공·고속도로 CCTV 자료가 이미 삭제되지 않도록 신속하게 확인하고 보존 절차를 지원하는 도구를 만든다.

제품의 중심은 영상에서 사용자를 자동으로 찾는 것이 아니다. GPS 경로, 사고 시점, 카메라 위치, 이동 시간, CCTV 시각 오차를 이용해 **보존을 요청하거나 사용자가 검토할 후보 시간·카메라를 산정하는 것**이다.

### 핵심 산출물

- 사건별 GPS 경로와 사고 시점 기록
- 주변 공식 CCTV 카탈로그
- 카메라별 예상 통과 시각과 확인 시간 범위
- CCTV 시각 오차·GPS 오차·계산 근거
- 공식 보존 요청의 상태와 참조번호
- 사용자가 직접 검토·확정한 사건 자료
- 조회·요청·열람·삭제 감사 로그

### 명시적 제외 범위

- 얼굴·번호판·차량 외형·보행 특성 기반 자동 식별
- 여러 CCTV에서 사람·차량의 이동 경로 자동 연결
- 사고와 무관한 타인의 이동 경로 장기 축적
- 비인가 접근, 로그인 우회, 비공식 스트림 추출
- 제공처 약관을 우회하는 대량 수집

## 3. 사용자 시나리오

### 시나리오 A: 사고 발생 후 보존 대상 산정

1. 사용자가 사고 시점과 위치를 입력하거나 GPS 기록에서 선택한다.
2. 시스템이 사고 전후의 경로와 주변 CCTV를 조회한다.
3. 카메라 위치, 이동 방향, 예상 도착 시간, GPS 오차, CCTV 시각 오차를 반영한다.
4. 시스템이 카메라별 보존 후보 시간 범위를 제안한다.
5. 사용자가 후보를 검토하고 공식 보존 요청을 준비한다.
6. 제공처의 응답·참조번호·보존 만료일을 사건에 연결한다.

### 시나리오 B: 운행 중 제한적인 사전 기록

1. 사용자가 명시적으로 기록을 시작한다.
2. GPS 경로와 CCTV 메타데이터만 최소한으로 기록한다.
3. 사고 버튼 또는 승인된 이벤트가 발생하면 사건을 생성한다.
4. 사건 전후의 제한된 범위만 보존 후보로 전환한다.
5. 평상시 자료는 짧은 보존 기간 후 자동 삭제한다.

### 시나리오 C: 제공처가 보존 요청만 지원

1. 시스템은 원본 영상을 다운로드하지 않는다.
2. 카메라 ID, 시간 범위, 위치, 사건 사유를 요청 양식에 채운다.
3. 사용자가 제공처의 공식 절차를 통해 요청을 제출한다.
4. 시스템은 요청 상태와 응답 증빙만 관리한다.

## 4. 요구사항

### 기능 요구사항

- FR-01: 사용자는 사건을 생성하고 사고 시점·위치·사유를 기록할 수 있어야 한다.
- FR-02: GPS 경로는 정확도 정보와 함께 저장하고 필요한 경우 위치 정밀도를 낮춰야 한다.
- FR-03: 공식 소스만 CCTV 카탈로그에 등록할 수 있어야 한다.
- FR-04: 각 소스는 제공처, 공식 엔드포인트, 약관 URL, 보존 요청 방식, 마지막 정책 확인 시각을 가져야 한다.
- FR-05: 사건 경로 주변 카메라를 검색할 수 있어야 한다.
- FR-06: 후보 카메라별 예상 통과 시각과 확인 시간 범위를 계산해야 한다.
- FR-07: 시간 범위 계산에는 GPS 오차, 이동 시간 오차, 카메라 시각 오차와 각 근거가 포함되어야 한다.
- FR-08: 정책 검증 실패·불명확·만료 상태에서는 자료 수집과 보존 요청을 거부해야 한다.
- FR-09: 공식 보존 요청의 제출 여부, 상태, 참조번호, 응답 시각을 관리해야 한다.
- FR-10: 초기 MVP는 영상 원본보다 메타데이터와 보존 요청을 우선해야 한다.
- FR-11: 모든 기록에는 보존 종료 시각이 있어야 한다.
- FR-12: 만료·철회·삭제 요청에 따른 삭제 작업과 결과를 기록해야 한다.
- FR-13: 조회, 수집, 요청, 열람, 내보내기, 삭제를 감사 로그로 기록해야 한다.

### 비기능 요구사항

- NFR-01: 사람·차량 자동 식별 또는 여러 카메라 간 자동 추적을 구현하지 않는다.
- NFR-02: 비밀정보는 소스 코드와 로그에 기록하지 않는다.
- NFR-03: 외부 요청은 TLS, 허용 목록, 제한된 재시도와 요청 빈도를 사용한다.
- NFR-04: 개발·테스트·운영 데이터와 권한을 분리한다.
- NFR-05: 삭제는 데이터베이스뿐 아니라 백업·캐시·파생 자료까지 고려한다.
- NFR-06: 구현되지 않은 보존 요청·영상 수집 기능을 동작하는 것처럼 문서화하지 않는다.
- NFR-07: 실제 인물·차량 식별을 요구하지 않는 테스트로 동작을 검증한다.

## 5. 시간 정합성 설계

### 입력 요소

- GPS 기록 시각과 정확도
- 사고 시점과 입력 신뢰도
- 카메라 좌표와 도로 방향
- 경로상의 예상 이동 속도·정체 가능성
- CCTV가 제공하는 시각 기준과 마지막 동기화 정보
- 영상·메타데이터의 제공 지연

### 계산 결과

각 후보에는 다음을 기록한다.

```text
camera_id
estimated_passage_at
camera_clock_offset_seconds
uncertainty_seconds
review_window_start
review_window_end
calculation_method
confidence
```

초기 버전은 복잡한 영상 분석 대신 보수적인 시간 범위를 제시한다. 시간 범위가 너무 넓어지면 자동 저장하지 않고 사용자 검토 또는 공식 제공처 문의로 전환한다.

### 금지되는 해석

후보 시간 범위가 계산되었다고 해서 영상 속 대상이 사용자라고 판단하지 않는다. 시스템은 “이 시간대 자료를 확인할 가치가 있음”만 제안하며, 영상 속 사람·차량의 동일성 판단은 자동화하지 않는다.

## 7. 의사결정 기록(ADR) 형식

중요한 설계 결정은 `docs/decisions/`에 다음 형식으로 기록한다.

```text
# ADR-XXXX: 제목

- 상태: 제안 | 승인 | 폐기
- 날짜:
- 결정자:

## 문맥

## 선택지

## 결정

## 결과와 위험

## 재검토 조건
```

기록된 결정(모두 '제안' 상태, 소유자 승인 필요):

- [ADR-0001](decisions/ADR-0001-local-cli-python-sqlite.md): 단일 사용자 로컬 CLI · Python 표준 라이브러리 · SQLite
- [ADR-0002](decisions/ADR-0002-time-basis-and-clock-offset.md): 시각 기준과 CCTV 시계 오차 모델
- [ADR-0003](decisions/ADR-0003-metadata-first-fail-closed.md): 메타데이터·보존 요청 초안 우선, 정책 검증은 실패 시 거부
- [ADR-0004](decisions/ADR-0004-location-precision-and-gps-gaps.md): 위치 정밀도와 GPS 공백 처리

기록해야 할 주요 결정 후보:

- 상시 영상 버퍼를 허용할지, 메타데이터만 기록할지
- 원본 좌표 대신 격자 좌표를 저장할 범위
- CCTV 시각 오차를 추정하는 방법과 신뢰도 표현
- 제공처 보존 요청과 직접 수집의 우선순위
- 사건 자료의 보존 기간과 내보내기 형식
- 단일 사용자용 로컬 도구와 서버형 운영 중 우선순위

## 8. 위험 관리

| 위험 | 기본 대응 |
|---|---|
| 공개 URL을 무단 저장 | 공식 정책과 저장 허용 범위 확인 전 어댑터 비활성화 |
| 자동 추적 기능으로 변질 | 영상 대상 식별 기능을 구현하지 않고 시간·위치 후보만 제공 |
| 개인 식별 가능성 | 원본보다 메타데이터 우선, 마스킹·접근 통제 |
| 위치 이력 노출 | 정밀도 축소, 짧은 보존, 사건별 권한 |
| CCTV 시계 오류 | 오차·근거·불확실성 기록, 보수적인 범위 제시 |
| 정책 변경 | 주기적 재검증과 실패 시 자동 중단 |
| 과도한 요청 | 속도 제한, 상한, 재시도 제한, 비상 중단 |
| 삭제 실패 | 삭제 재시도, 검증 보고서, 운영자 알림 |
| 비밀정보 유출 | 환경 변수·비밀 저장소·커밋 검사 |
| 증거성 오해 | 원본성·진본성을 보증하지 않으며 공식 절차를 우선한다고 명시 |

## 9. 검토 게이트

### 법률·정책 게이트

- 제공처의 공식 이용 조건과 보존 요청 절차를 확인했는가?
- 저장·재생·재배포 허용 범위가 명확한가?
- 위치정보와 영상정보 처리의 근거가 있는가?
- 삭제 요청과 철회 절차가 정의되었는가?

### 개인정보 게이트

- 개인 식별 없이 사고 증거 보존 목적을 달성할 수 있는가?
- 원본보다 덜 민감한 대체 데이터가 있는가?
- 사고 전후의 최소 시간·공간 범위만 처리하는가?
- 접근 주체와 감사 방법이 정의되었는가?

### 시간 정합성 게이트

- GPS 정확도와 카메라 위치가 기록되는가?
- CCTV 시각 기준과 오차 추정 근거가 있는가?
- 도착 시각 계산이 보수적인가?
- 후보 범위를 자동 식별 결과로 오해하지 않도록 표시하는가?

### 보안 게이트

- 인증·권한·키 관리가 최소 권한인가?
- 외부 요청의 도메인과 빈도가 제한되는가?
- 장애 시 수집과 보존 요청이 안전하게 중단되는가?
- 삭제가 저장소·백업·캐시 전체에 적용되는가?

## 10. 테스트 계획

- 단위: 거리 계산, 이동 시간 범위, 좌표 정밀도 축소, 시각 오차 계산, 정책 판정, 보존 만료
- 계약 테스트: 공식 어댑터의 응답을 비식별 fixture로 검증
- 통합: 합성 경로에서 카메라 후보 검색부터 삭제까지 검증
- 보안: 비밀정보 로그 노출, 권한 상승, 허용 목록 우회 방지
- 운영: API 장애, 약관 만료, 네트워크 지연, 삭제 실패
- 회귀: 제공처 스키마 변경과 정책 변경
- 오해 방지: 후보 시간 계산 결과가 자동 식별·추적 결과로 표시되지 않는지 검증

## 12. 완료 정의

기능이 “완료”되었다고 말하려면 다음을 모두 만족해야 한다.

- 구현·문서·테스트가 같은 범위를 설명한다.
- 구현되지 않은 기능은 README에서 예정 또는 TODO로 표시된다.
- 시스템이 영상 속 사람·차량을 자동으로 식별하거나 여러 카메라 사이에서 추적하지 않는다.
- 정책이 불명확한 입력을 안전하게 거부한다.
- GPS·카메라 위치·시각 오차와 계산 근거를 확인할 수 있다.
- 개인정보와 비밀정보가 테스트·로그·예제에 포함되지 않는다.
- 보존 만료와 삭제 요청을 재현하고 검증할 수 있다.
- 담당자가 소스별 법률·약관 검토 근거와 공식 요청 절차를 찾을 수 있다.
- 사건 자료가 법적 증거로 자동 인정된다고 오해할 표현이 없다.

### 13.2 의도적으로 남긴 범위

- 영상·스틸 수집, 제공처 자동 제출, HTTP 어댑터, 저장 시 암호화는 구현하지 않았다(M2~M3).
- 카메라 촬영 방향·화각은 고려하지 않고 원형 반경만 쓴다. 카탈로그가 방향 정보를 제공하면 재검토한다.

### 13.3 열린 질문 (소유자 결정 필요)

1. **시나리오 B(운행 중 상시 경로 기록)**: 현재 데이터 모델은 경로 지점이 사건에만 속해, 사고 전에 미리 기록하는 흐름을 표현할 수 없다. 별도 "기록 세션(trip)"과 짧은 보존 기간을 두고 사고 시 해당 구간만 사건으로 복사하는 방식을 제안한다. 구현할지 결정이 필요하다.
2. **기본값 승인**: 사건 보존 90일(최대 3년), 경로 좌표 소수점 4자리, 촬영 반경 100m, GPS 정확도 미상 시 25m, 시각 근거 없음 ±180초, 보존 요청 범위 상한 15분, 감사 로그 365일.
3. **첫 공식 제공처**: 어느 기관·서비스를 M2 대상으로 할지, 그리고 그 제공처가 보존 요청을 표준시·화면 표시 시각 중 무엇으로 받는지.
4. **라이선스**: 아직 정해지지 않았다.

## 14. 방향 전환: GPS 기반 실시간 자동 녹화 (2026-10-27)

소유자 요청: "GPS 데이터만 보내면(Traccar 앱 등) 내가 지나가든 내 차가 지나가든 CCTV를 확인하다가,
맞으면 지나가는 동안(+앞뒤 1~2초) 저장하는 구조를 전자동으로." 결정 내용은
[ADR-0005](decisions/ADR-0005-automatic-live-recording.md).

### 14.1 구현(v0.2)

- `gps2cctv serve`: Traccar(OsmAnd) GPS 수신 → 주변 ITS 카메라 갱신 → 앞쪽 카메라 녹화 대기 →
  통과 구간 [진입−2초, 이탈+2초] ± 시각 오차 저장(원본 + mp4 + 근거 JSON)
- 급정거·SOS·수동 표시 → 클립 보호, 사건·보존 요청 후보 자동 생성
- 자동 삭제(클립·위치 14일, 용량 20GB), Docker 실행
- 13.3의 열린 질문 1(시나리오 B, 상시 경로 기록)은 `position` 표와 자동 사건 생성으로 해결

### 14.2 검증

- 시뮬레이션 테스트: 가짜 시계 + 가짜 실시간 HLS로 통과 구간·세그먼트 선택·정차·급정거·정책 차단·스트림 장애 확인
- 통합 테스트: ffmpeg 실시간 HLS + 실제 HTTP GPS 전송 → mp4 길이를 ffprobe로 확인

### 14.3 남은 일

1. 실제 ITS 키로 첫 실행: 응답 형식, `cctv_type`(4/1), 스트림 지연·시각 태그 여부 확인 후 기본값 조정
2. 실제 주행 1회: 통과 클립에 차량이 실제로 들어오는지 확인(앞뒤 여유 조정)
3. 지자체 CCTV 오픈 API 추가 여부(예: 경기도 교통정보)
4. 클립 열람용 간단한 웹 화면(인증 포함) 여부
