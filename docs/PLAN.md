# 프로젝트 실행 계획

## 1. 문서 상태

- 상태: 초안
- 기준일: 2026-10-26
- 범위: 공식적으로 공개·허가된 CCTV 메타데이터와 제한적인 자료 보존
- 우선순위: 안전성, 합법성, 최소 수집, 삭제 가능성

## 2. 제품 정의

이 프로젝트는 GPS 또는 사용자가 입력한 위치 주변의 공식 CCTV 정보를 검색하고, 제공처의 정책과 권한을 확인한 뒤 허용된 범위에서 메타데이터를 기록하는 도구를 지향한다.

핵심 산출물은 “사람을 찾는 영상 감시 시스템”이 아니라 다음과 같다.

- 공식 CCTV 소스 카탈로그
- 위치 기반 카메라 검색 결과
- 소스별 정책·권한 상태
- 보존 기한이 있는 관찰 기록
- 조회·수집·삭제 감사 로그

개인 식별, 얼굴·번호판 인식, 타인의 이동 추적, 무단 영상 저장은 제품 범위에서 제외한다.

## 3. 요구사항

### 기능 요구사항

- FR-01: 관리자는 공식 소스만 카탈로그에 등록할 수 있어야 한다.
- FR-02: 각 소스는 제공처, 공식 엔드포인트, 약관 URL, 마지막 정책 확인 시각을 가져야 한다.
- FR-03: 사용자는 위치와 검색 반경을 제공해 주변 카메라를 조회할 수 있어야 한다.
- FR-04: 검색 결과는 카메라 위치를 필요 이상으로 정밀하게 노출하지 않아야 한다.
- FR-05: 수집 전 소스 정책과 사용자 권한을 검증해야 한다.
- FR-06: 정책 검증 실패·불명확·만료 상태에서는 수집을 거부해야 한다.
- FR-07: 초기 MVP는 영상 원본이 아닌 메타데이터와 이벤트를 우선 저장해야 한다.
- FR-08: 모든 기록에는 보존 종료 시각이 있어야 한다.
- FR-09: 만료·철회·삭제 요청에 따른 삭제 작업을 수행하고 결과를 기록해야 한다.
- FR-10: 조회, 수집, 열람, 내보내기, 삭제를 감사 로그로 기록해야 한다.

### 비기능 요구사항

- NFR-01: 비밀정보는 소스 코드와 로그에 기록하지 않는다.
- NFR-02: 네트워크 요청은 TLS, 허용 목록, 제한된 재시도와 요청 빈도를 사용한다.
- NFR-03: 모든 외부 연동은 공식 문서의 정책과 장애 대응 기준을 따른다.
- NFR-04: 개발·테스트·운영 데이터와 권한을 분리한다.
- NFR-05: 삭제는 데이터베이스뿐 아니라 백업·캐시·파생 자료까지 고려한다.
- NFR-06: 실제 인물·차량 식별을 요구하지 않는 테스트로 동작을 검증한다.

## 5. 의사결정 기록(ADR) 형식

중요한 설계 결정은 아래 형식으로 `docs/decisions/`에 기록한다.

```text
# ADR-XXXX: 제목

- 상태: 제안 | 승인 | 폐기
- 날짜:
- 결정자:

## 문맥

## 선택지

## 결정

## 결과와 위험

## 재검토 조건
```

기록해야 할 주요 결정 후보:

- 원본 좌표를 저장할지, 격자 좌표만 저장할지
- 원본 영상 대신 이벤트·스틸을 우선할지
- 제공처 약관 변경을 어떻게 감지할지
- 보존 기간과 삭제 검증 범위
- 단일 사용자용 로컬 도구와 서버형 운영 중 어느 쪽을 우선할지

## 6. 위험 관리

| 위험 | 기본 대응 |
|---|---|
| 공개 URL을 무단 저장 | 공식 정책 확인 전 어댑터 비활성화 |
| 개인 식별 가능성 | 식별 기능 배제, 마스킹·메타데이터 우선 |
| 위치 이력 노출 | 정밀도 축소, 짧은 보존, 접근 통제 |
| 정책 변경 | 주기적 재검증과 실패 시 자동 중단 |
| 과도한 요청 | 속도 제한, 상한, 지수 백오프, 비상 중단 |
| 삭제 실패 | 삭제 재시도, 검증 보고서, 운영자 알림 |
| 비밀정보 유출 | 환경 변수·비밀 저장소·커밋 검사 |
| 기능의 목적 외 사용 | 사용자 확인, 허용 목록, 문서화된 금지 범위 |

## 7. 검토 게이트

다음 게이트를 통과하지 못하면 다음 단계로 진행하지 않는다.

### 법률·정책 게이트

- 제공처의 공식 이용 조건을 확인했는가?
- 저장·재생·재배포 허용 범위가 명확한가?
- 위치정보와 영상정보 처리의 근거가 있는가?
- 삭제 요청과 철회 절차가 정의되었는가?

### 개인정보 게이트

- 개인 식별이 기능적으로 불필요한가?
- 원본보다 덜 민감한 대체 데이터가 있는가?
- 수집 목적·범위·보존 기간이 명확한가?
- 접근 주체와 감사 방법이 정의되었는가?

### 보안 게이트

- 인증·권한·키 관리가 최소 권한인가?
- 외부 요청의 도메인과 빈도가 제한되는가?
- 장애 시 수집이 안전하게 중단되는가?
- 삭제가 저장소·백업·캐시 전체에 적용되는가?

## 8. 테스트 계획

- 단위: 거리 계산, 좌표 정밀도 축소, 정책 판정, 보존 만료
- 계약 테스트: 공식 어댑터의 응답을 비식별 fixture로 검증
- 통합: 합성 카탈로그에서 검색부터 삭제까지 검증
- 보안: 비밀정보 로그 노출, 권한 상승, 허용 목록 우회 방지
- 운영: API 장애, 약관 만료, 네트워크 지연, 삭제 실패
- 회귀: 제공처 스키마 변경과 정책 변경

테스트 fixture에는 실제 사람·차량의 식별 가능한 영상이나 위치 이력을 사용하지 않는다.

## 10. 완료 정의

기능이 “완료”되었다고 말하려면 다음을 모두 만족해야 한다.

- 구현·문서·테스트가 같은 범위를 설명한다.
- 구현되지 않은 기능은 README에서 예정 또는 TODO로 표시된다.
- 정책이 불명확한 입력을 안전하게 거부한다.
- 개인정보와 비밀정보가 테스트·로그·예제에 포함되지 않는다.
- 보존 만료와 삭제 요청을 재현하고 검증할 수 있다.
- 담당자가 소스별 법률·약관 검토 근거를 찾을 수 있다.
